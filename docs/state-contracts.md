# Persistent State Contracts

This document publishes the Stage 1 identity, entity-state and faction-standing interfaces for consumers. These contracts are in-memory only; save envelopes, disk writes and migrations belong to CORE-03/04.

## Entity registry

`EntityRegistry` in `res://persistence/entity_registry.gd` is a `RefCounted` data service. It owns no scene Nodes and does not derive IDs from scene paths, chunk order or load order.

- `register_entity(uuid: String, initial_state: Dictionary) -> void` accepts one canonical, lowercase UUID (RFC 4122 textual form, version nibble 1–8, valid variant nibble). IDs are authored/generated identity tokens and remain stable across unload and restart. Invalid IDs and invalid records warn and are ignored. A duplicate warns and preserves the first record exactly, including later modifications.
- `get_entity_state(uuid: String) -> Dictionary` returns a deep copy. Unknown or invalid IDs return `{}`. Mutating the returned dictionary cannot change registry truth.
- `has_entity(uuid: String) -> bool` reports whether a valid ID is registered.
- `commit_state_delta(uuid: String, delta: Dictionary) -> void` ignores unknown IDs and invalid deltas with a warning. A valid top-level dictionary delta merges recursively where both old and new values are dictionaries. Scalars and arrays replace their prior values; `null` is a value and replaces. The entire merged result is validated before commit, so invalid updates have no partial effect.
- `try_commit_state_delta(uuid: String, delta: Dictionary) -> bool` uses the same validation/merge path and returns false on rejection or true on acceptance, including a valid no-op. The original void method delegates to it. WORLD-03 uses this result to avoid projecting a rejected authority update; no second merge implementation or state owner is introduced.

Entity records use JSON-like values only: `null`, booleans, signed 64-bit integers, finite floats, UTF-8 strings, arrays and dictionaries with string keys. Nodes, all other Objects, packed arrays and engine-specific values are rejected. Bounds are 16 nested container levels, 1,024 entries per container, 10,000 values in one submitted record/delta, 16 KiB per string and 256 bytes per dictionary key. The merged record must also fit these bounds. These engineering limits constrain memory and recursion; they are not gameplay balance values.

UUID policy: IDs must be allocated independently of runtime Nodes and retained by authored records or the persistence layer. This contract validates canonical format but does not mint IDs, guarantee global uniqueness across external sources or provide collision recovery. Callers should generate an ID once and persist it with their authoritative record.

## Faction standings

`FactionState` in `res://persistence/faction_state.gd` stores integer standings for the faction IDs supplied when constructed. IDs are non-empty and have no leading or trailing whitespace. Unknown IDs are not implicitly created.

- `get_faction_standing(faction_id: String) -> int` returns `0` for unknown IDs (neutral read behavior).
- `set_faction_standing(faction_id: String, standing: int) -> bool` clamps known faction values to `-100..100`; it returns `false` for unknown IDs.
- `adjust_faction_standing(faction_id: String, delta: int) -> bool` applies an integer delta and clamps the result to `-100..100`; it returns `false` for unknown IDs.
- `is_hostile(faction_id: String) -> bool` is true at or below the hostile threshold; `is_allied(faction_id: String) -> bool` is true at or above the allied threshold. Unknown IDs are false for both queries.
- `configure_thresholds(hostile_threshold: int, allied_threshold: int) -> bool` accepts values inside `-100..100` only when hostile is strictly less than allied. Invalid configurations return false without changing thresholds.

The configurable engineering defaults are hostile `-50` inclusive and allied `+50` inclusive. Values between thresholds are neutral. These defaults make boundaries explicit for consumers and tests; they are tuning defaults, not approved balance. Faction records and entity records remain data-only. Save serialization and ownership integration are deferred to CORE-03/04.

## Save envelope and SaveStore (CORE-03)

`SaveStore` in `res://persistence/save_store.gd` stores one snapshot per integer slot `0..99` under `user://saves/slot_NN.save` (or an injected directory). Its exact entry points are `save_to_disk(slot: int) -> Error` and `load_from_disk(slot: int) -> Error`. The constructor accepts a no-argument snapshot provider, a candidate validator, a single atomic-apply callback, and an optional filesystem adapter with atomic same-directory replacement for deterministic failure tests.

A v1 file is UTF-8 JSON with this outer shape: `{ "format": "cyberpunk-save", "version": "1", "payload": <tagged value> }`. Version is a decimal string so the JSON parser cannot reinterpret it as a float. `payload` is a tagged tree: every value is encoded explicitly as `nil`, `bool`, `int`, `float64le`, `string`, `array`, or `dict`; signed integers are stored as decimal strings and floats as eight-byte little-endian hex strings. Arrays contain encoded values. Dictionaries contain `[string_key, encoded_value]` pairs, allowing all payload keys to remain unambiguous. This preserves signed int64 values and float types without JSON-number coercion. Objects, Nodes, packed arrays, non-finite floats, non-string keys, malformed tags, duplicate dictionary keys, oversized containers and over-depth values are rejected. The codec allows three levels of envelope depth around entity data and still limits each entity state to the registry depth of 16. The root snapshot requires four fields: `player` (dictionary), `entities` (array of `{uuid, state}` dictionaries), `factions` (dictionary of faction ID to integer standing in `-100..100`), and `domains` (dictionary). Entity UUIDs must follow the canonical lowercase UUID policy above and be unique within the candidate.

`save_to_disk` validates the provider snapshot, writes a sibling temporary file, then atomically renames it over the slot within the same directory. A failed temporary write or failed atomic replacement leaves the prior slot untouched. If the process stops before replacement, the prior slot remains and the temporary file is ignored; after replacement, the new complete slot is visible. `load_from_disk` parses, decodes, structurally validates, and passes a deep copy to the consumer validator before it invokes the apply callback. A validator must be pure and must not mutate live state. The apply callback receives a fully validated deep copy and must prepare and commit it as one atomic operation, without per-record commits or fallible steps. SaveStore invokes that callback only after all disk and consumer validation succeeds, so missing, malformed, truncated, unsupported-version, invalid-slot and duplicate-UUID inputs do not partially change live state. Future versions return `ERR_UNAVAILABLE`; unknown older versions return `ERR_FILE_UNRECOGNIZED`.

## Migrations and domain snapshot adapters (CORE-04)

`SaveMigrations` is a pure ordered transformer from an envelope source version and decoded data dictionary to `{ok, error, version, snapshot}`. Its accepted current version is the SaveStore v1. The retained v0 fixture uses the same tagged value codec but predates the root `domains` field: it has `domain_records` instead. The single v0→v1 step requires player/entity/faction records and a dictionary `domain_records`, renames that dictionary to `domains`, and preserves every entry and other root record. Missing steps reject as `ERR_FILE_UNRECOGNIZED`; future source versions reject as `ERR_UNAVAILABLE`. A migration never writes the file. `SaveStore` runs it after data decoding and before v1 snapshot validation; a failed transformation leaves both source bytes and live owners untouched. A successful old-file load also leaves source bytes intact until a later explicit save.

`SnapshotAdapters` is callback glue over existing owners, not a state store. `EntityRegistry` and `FactionState` remain authoritative and expose copy-out snapshots, pure validation, prepared replacements, and a no-signal/no-fail commit phase. Adapter capture returns the v1 root keys `player`, `entities`, `factions`, and `domains`. The player callback owns `player`; registry and faction instances own `entities` and `factions`; the domain callback coordinates actual domain owners. Planned domain keys are `inventory`, `missions`, `npc_memory`, and `active_hacks`, all as data dictionaries. Stage 1 currently uses fixture/mock player and domain callbacks; no inventory, mission, NPC-memory, or hack gameplay integration is claimed.

Optional extension capture/prepare/commit callbacks retain root records outside those four owned keys. Configure all three callbacks together; partial configuration rejects. The extension owner must preserve opaque recoverable root records through prepare, commit, recapture and explicit save. Extension capture cannot overwrite an owned root key. Without an extension owner, a candidate containing unknown root records rejects before any mutation, rather than silently dropping data. Unknown domain records remain the domain coordinator's responsibility. The adapter itself retains no additional authoritative state.

A rejected migration must return a nonzero load error. If its result omits an integer error or contradicts rejection with `error: OK`, SaveStore returns `ERR_FILE_UNRECOGNIZED`; it never reports a successful load without applying the candidate. This failure path leaves source bytes and live state intact.

Each callback owner must return deep copies from capture. Its prepare callback validates and returns `{ok: true, prepared: <data>}` without changing live state; commit receives that prepared value and must be infallible, void, and emit no signals. The adapter prepares every participant first, then swaps registry, faction, player, and domain state in one synchronous commit call. Any preparation rejection returns false before the first swap, and SaveStore treats a boolean false apply result as a rejected load. Consumers must defer notifications until all owners have swapped. A domain coordinator may apply only keys for which it has an authoritative owner; it must preserve opaque unknown recoverable domain records rather than claim they were applied to an unknown runtime service. These contracts do not create gameplay owners for unimplemented domains.

Snapshot values remain data-only and preserve `int` and `float` types through deep copies. The complete decoded/migrated root is bounded by the SaveStore envelope: 16 MiB file size; at most 19 nested value levels (the registry's 16 entity-state levels plus three envelope levels); at most 1,024 entries per container; 10,000 visited values; 16 KiB UTF-8 strings; and 256-byte dictionary keys. Each entity state is additionally validated against the registry's own 16-level, 10,000-value limit. Migration output is checked against the same v1 root limits before any callback runs.

### Timed-effect clock policy

Persist remaining durations, not wall-clock deadlines. Remaining time is paused while an entity or effect is unloaded and while the game is offline; only the active, unpaused simulation clock advances it. On load/re-entry, the saved remainder resumes from that clock. This is an engineering default for HACK-05 and related timed effects, not approved gameplay balance. It avoids offline expiration and wall-clock changes until an owning gameplay task explicitly introduces a different clock contract.
